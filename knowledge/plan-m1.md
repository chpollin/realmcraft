# Plan M1, complete playable game

Binding plan and contract of milestone M1. Lanes build against the contracts below. A lane that needs to depart from a contract says so to the integrator before it builds, and the integrator records the change here. Orientation for the game itself lives in `docs/Spieldesign.md`, `docs/Regelkern.md`, `docs/Agentenvertrag.md` and `docs/Harness.md`.

## Goal

M1 turns the existing kernel, harness and board into one game a player can start, play and finish in the browser. The game stays turn-based, the kernel stays the only writer of campaign state, peoples develop without a fixed tree, and every decision shows its consequences before it is taken (D15).

## Acceptance criteria

1. A new game starts in the browser. The start screen offers world package, seed with a random button, people from the package start templates, rivals and difficulty. The server creates the campaign through `engine/cli.mjs new`, and the board opens it.
2. Continue lists the existing campaigns and opens the chosen one. Existing campaigns, including `hochland-1`, load after a `repin` without loss.
3. A turn runs end to end with the harness (`/zug`). Phase A, the agents of phase B, the judges and the next planning step show on the board.
4. The board shows the six paths as a wheel with tier, achievements, research in progress and research points. Research is assigned and directed from the wheel.
5. Every module is usable through the board without the CLI, namely orders and probes, council and talks, trade, military, magic, way of life, provinces and conquest on the map, event cards with choices, and Bestimmungen including the revealed destinies of rivals.
6. Every refusal the kernel gives appears as a localized label built from a machine-readable code, never as parsed English text.
7. The campaign ends in a victory or a collapse screen built from the kernel result, with a summary of the campaign.
8. The UI runs in English by default and in German when chosen in the settings. The narrative language is a campaign setting.
9. Audio plays ambience, UI feedback, dice and stingers, synthesized in the browser, with mute, volumes and reduced intensity under reduced motion.
10. Playtest entries 1 to 22 in `docs/spieltests/2026-10-03-spielbrett.md` are implemented or answered with a recorded decision.
11. All gates below are green on main after the last merge.

## Kernel contracts

All additions are optional in the schemas with a stated default, so states and content written before M1 stay valid. The kernel writes the new fields on every write. `RULES_VERSION` does not move.

### Paths in the world package

`regeln.json` gains an optional `pfade` block, validated by `engine/schemas/world.js`:

```js
pfade: obj({
  paths: arr(obj({
    id: ref('id'),
    tags: arr(ref('tag'), 16, 1),
    // null: always open. Otherwise open from the first season in which the
    // practice ledger sums at least `min` over these tags.
    opens: nullable(obj({ practice: arr(ref('tag'), 8, 1), min: int(1, 99) })),
  }), 8, 1),
  // unlock[k-1]: completed achievements on the path of tier k-1 or higher
  // that open tier k on the path. unlock[0] is 0.
  unlock: arr(int(0, 20), 5, 1),
  // Path of an Entwicklung whose tags meet no path.
  fallback: ref('id'),
})
```

The validator checks unique path ids, every tag in the vocabulary, `fallback` naming a path, `unlock[0] === 0`, and a world label `pfad.<id>` for every path. A world without the block has no paths, and research behaves as before M1.

Hochland ships the six paths in this order, which is also the tie-break order and the order of the wheel. C may revise the tag lists in wave 2.

| id | tags | opens |
|---|---|---|
| `nahrung` | nahrung, weide, herde, winter, wetter, bleiben, zug | null |
| `gemeinschaft` | ordnung, rat, bund, verhandlung, siedlung, machtprobe, unfreiheit, vertragsbruch | null |
| `militaer` | angriff, verteidigung, befestigung, belagerung, hinterhalt, krieg, fuss, schuetzen, beute, befohlen | null |
| `werk` | bau, erz, pulver, weg, glut, salz, markt, handel | null |
| `erkenntnis` | erkundung, wandel, bestimmung | null |
| `magie` | magie, schau, feuer, dunkel, opfer | practice magie, schau, feuer, dunkel, opfer, min 1 |

`unlock` is `[0, 2, 2, 2, 2]`, `fallback` is `gemeinschaft`.

### Path of an achievement

`engine/schemas/entwicklung.js` gains an optional `pfad` (path id) on the envelope. `pfadOf(env, ent)` in `engine/core/pfade.js` returns, in this order, the explicit `pfad`, the path with the most tags in common with `ent.tags` (ties by path order), or `fallback`. Without a `pfade` block it returns null. The research agent sets `pfad` on every new proposal, the validator rejects an unknown `pfad` as `dangling_ref`.

### Path state in the campaign

`people.pfade` is optional with the default `{ opened: {} }`:

```js
pfade: obj({ opened: map(ref('id'), ref('turn')) })
```

`opened[pathId]` is the turn a path with an `opens` condition opened. The latch never closes. A path opens in the research step of a season when its practice condition holds over the ledger, or when the people knows an active achievement on it. Paths without `opens` need no entry. Everything else about a path derives from known achievements, so nothing else is stored.

`developments.requests[]` gains an optional `pfad` (path id or absent).

### Path tier and gating

For people `pid` and path `P`:

- `done(P, k)` counts the active known achievements on `P` with tier at least `k`.
- `pathTier(P)` is the highest `k` such that `done(P, j-1) >= unlock[j-1]` holds for every `j` from 1 to `k`, at most `MAX_TIER`.
- `cap(P) = min(pathTier(P), openTier(state, env, pid))`, the highest tier researchable on `P`.

Gating applies when something enters the candidate list. `offerPool` skips world achievements above `cap(P)` or on a path that is not open. The content validator rejects an agent proposal for a people with `pfad_tier` (params `pfad`, `tier`, `cap`) or `pfad_closed` (params `pfad`). Candidates and research already listed before M1 stay valid, so a migrated campaign never loses a project.

### Research points and accumulation

Research points of a season stay the existing figure of `resolveResearch`, `researchBase + labour + mods + knowledge`. `labour` is the clans assigned to `research` times `researchPerClan`, `mods` the standing `research.mod` effects whose tags meet the project, `knowledge` the Wissen burned from stock, at most `tune(env, 'knowledgeSpend')`. Points flow into the first project of `developments.research` and accumulate across seasons until the effective cost `researchCost` is reached. The cost already rises with tier through `cost.research` and with the number of known achievements. Completion is unchanged, with resources paid at completion and the effect from the next turn.

### Research orders

| Order | Slot | Params | Change in M1 |
|---|---|---|---|
| `research.assign` | free, unique | `{ development: ref }`, an open candidate or a project in research | Issues carry `params.reason` (`not-candidate`) and `params.development`. A new assignment in the same draft replaces the old one on the board, the kernel rule stays one per season. |
| `research.direct` | free, unique | `{ pfad?: pathId, tags?: tag[1..3], note?: string up to 200 }`, at least one of `pfad` and `tags` | `pfad` must name an open path (`target`, reason `pfad-closed`). With `pfad` alone the request takes the first three tags of the path that are in the vocabulary. The request is stored as `{ turn, tags, note, pfad }`. |

### Derived path view

`computeDerived` writes `derived[pid].pfade`, so the projection carries it and the board reads it without recomputing. The same object comes from `pathsView(state, env, pid)` in `engine/core/pfade.js`, which runs on a projection as well.

```js
derived[pid].pfade = {
  points: { base, labour, knowledge, total },   // next season, before per-project research.mod
  paths: [{
    id,                       // path id in regeln order
    open,                     // boolean
    openedAt,                 // turn or null
    tier,                     // pathTier
    cap,                      // min(pathTier, openTier)
    done,                     // active known achievements on the path
    next,                     // { tier, needed } towards the next path tier, or null at the top
    known, research, candidates,   // refs on this path
  }],
}
```

The `entwicklungen` view adds `pfad` to every entry and the section `pfade` with the same object.

The research task (`engine/harness/tasks.js`) adds `context.pfade` with this object and the path of each request, so the agent proposes on open paths within `cap`.

### Machine-readable issues

`issue(code, path, message, { severity, refs, params })` returns `{ code, severity, path, message, params?, refs? }`. `params` is a flat object of strings, numbers, booleans or string arrays and is present whenever the message interpolates a value. Generic codes such as `target` and `cost` name the concrete refusal in `params.reason`, a kebab-case key. `message` stays English for logs and agents. Every issue the kernel returns from `checkDraft`, `preview`, the CLI and the modules carries the params its message uses.

Label keys follow the existing rule that keys have no underscore:

- `issue.<code>` with `_` written as `-`, so `free_slots` becomes `issue.free-slots` and `handel.no_route` becomes `issue.handel.no-route`.
- With `params.reason` the board first looks up `issue.<code>.<reason>`, then `issue.<code>`.
- Placeholders in a label are `{name}` and are filled from `params`.

Issue labels live in the board's label files (lane I), not in the world labels.

Severity of kernel issues stays `error` or `warning`. Judges' findings carry `info`, `warn` or `severe`. `status.json` gains an optional `steps[].findings`, a list of `{ id, judge, severity, text, refs }`, which `engine/harness/status.js` writes from accepted finding items.

### View additions for the board

All of them sit in `derived[pid]` and reach the board through the projection.

| Key | Shape | Rule |
|---|---|---|
| `council` | `[{ id, location: { tile, settlement }, strengths: { lead, favor, oppose } }]` | `location` is the tile of `member.at` or of the home settlement. `member.at` is an optional state field (default null), set at resolution to the target tile of the order the member led and cleared at the next open. `strengths.lead` is the lead modifier the probe would use, `favor` and `oppose` are the goal tags. |
| `trade` | `{ routes: [{ partner, length, roads, reachable, reason }], orders: [type] }` | One row per people in contact. `reason` is an issue code or null. `orders` lists the trade order types the catalogue allows now, their parameter candidates come from the catalogue. |
| `rivals` | `[{ people, destiny: null or { ref, name, milestones: [{ id, text, reached }] } }]` | A rival's destiny is revealed when the peoples have contact and the rival has reached a milestone, or while a reveal of scope people covers it. Otherwise `destiny` is null. |
| `outcome` | null while playing, otherwise `{ kind, winner, won, turn, reason, summary }` | `summary` is `{ turns, worldYear, population, regions, settlements, achievements: { <pathId>: n }, destiny: { ref, name, reached, of } or null, highlights: [logEntryId] }`, with at most eight highlights of kinds `research.completed`, `bestimmung.reached`, `bestimmung.fulfilled`, `region.control`, `people.collapsed`. |

`preview` honours `draft.choices` and `destiny.adopt`. The forecast includes the once effects of the chosen options, and the result gains `choices: [{ id, option, delta }]`. The row of a `destiny.adopt` order gains `destiny: { ref, name, milestones, delta }`. `delta` is `{ resources, meters, loyalty, population, tokens, statuses }` with only the keys that change.

### New game options and settings

`state.settings` is optional with the default `{ difficulty: 'normal', language: 'de' }`, with `difficulty` one of `easy`, `normal`, `hard` and `language` a two-letter code. `createCampaign(env, { id, seed, player, rivals, difficulty, language })` takes `rivals` as template ids of the other peoples (default all) and scales the start stock of AI peoples by difficulty. `engine/cli.mjs new` takes `--rivals a,b`, `--difficulty` and `--lang` and validates them at the boundary. The harness tells narrative agents to write in `settings.language`.

### Migration

Readers treat absent fields as their defaults, through one helper per field in the owning lane (`pfadeOf(people)` for K1, `settingsOf(state)` for K2). The next kernel write stores them. Changing `welten/hochland` moves the package hash, so an existing campaign needs `node engine/cli.mjs repin --campaign <id>` before the next transition. The repin of `hochland-1` is an owner action, no lane runs it on `campaigns/`. K1's migration test builds a campaign in a temp dir with the pre-M1 shape (new fields removed, the pre-M1 world package hash), runs `repin`, a full turn and `status`, and checks that known achievements, research and candidates survive and that every path is assigned.
